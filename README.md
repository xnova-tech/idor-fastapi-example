# IDOR: проверка доступа к заказу

Учебный пример XNova показывает разницу между успешной аутентификацией и правом читать конкретный заказ. В памяти находятся два вымышленных пользователя и два заказа. В уязвимом варианте пользователь A получает заказ B; исправленный обработчик возвращает одинаковый `404` для чужого и отсутствующего заказа.

Пример запускается только через `FastAPI TestClient`: он не открывает HTTP-порт и не обращается к внешнему сервису. Уязвимый режим принимает запросы только от встроенного клиента `testclient`; при другом клиентском адресе он возвращает `403` до чтения заказа. Демонстрационные токены `demo-a` и `demo-b` не подходят для аутентификации в рабочем сервисе.

## Подготовка

Проверенное окружение: Python 3.12.12, FastAPI 0.128.2, Starlette 0.50.0, HTTPX 0.28.1, pytest 9.1.1. Все версии зависимостей закреплены в `requirements.txt`.

На macOS или Linux выполните:

```bash
git clone https://github.com/xnova-tech/idor-fastapi-example.git
cd idor-fastapi-example
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m examples.check_idor
.venv/bin/python -m pytest -q
```

На Windows используйте `py -3.12 -m venv .venv`, затем замените `.venv/bin/python` на `.venv\Scripts\python.exe` в остальных командах.

## Ожидаемое наблюдение

Проверка двух вариантов выводит, среди прочего:

```text
vulnerable_a_foreign: status=200 order_id=202
fixed_a_foreign: status=404 order_id=None
fixed_anonymous: status=401 order_id=None
```

После проверки регрессии итоговая строка pytest содержит `10 passed`. В набор входят доступ к своему заказу, отказ для чужого и отсутствующего заказа, отсутствие или ошибка токена, очистка подменённой зависимости, отрицательный контроль уязвимой версии и проверка обоих режимов с другим клиентским адресом.

Ключевое исправление находится в `examples/idor_app.py`: сервер сравнивает `owner_id` найденного заказа с пользователем, полученным из зависимости `current_user`, до возврата ответа. ID из URL или сложный UUID не дают права на объект сами по себе.

## Если проверка не проходит

- `ModuleNotFoundError: fastapi` или `httpx`: установите зависимости тем же Python из `.venv`, которым запускаете скрипт.
- `ModuleNotFoundError: examples`: запускайте команды из корня репозитория, где лежат `pytest.ini` и каталог `examples`.
- Чужой заказ вернулся с `200` в исправленном варианте: проверьте условие владельца в `get_order` и убедитесь, что вызван `make_app()` без уязвимого режима.
- Вместо десяти тестов вы получили ошибку установки: проверьте версию Python и повторите установку из закреплённого `requirements.txt`.

`Dockerfile.verify` описывает отдельное окружение для проверки с закреплённым базовым образом. Не запускайте уязвимый вариант как сервис: все необходимые наблюдения получаются локальными запросами TestClient.
